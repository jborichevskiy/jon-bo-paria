# Paria Canyon Trip Map — Project Context

## What this is

A custom interactive trip artifact for a Paria Canyon backpacking trip (April 2026), built as a single self-contained HTML file. The goal is something onX can't produce: a personal, shareable map with your photos, your story, and your styling — that you own end-to-end.

## The trip

- **Route**: White House Trailhead → Paria Canyon → Lees Ferry
- **Distance**: ~38 miles, south-southwest through the Paria Canyon–Vermilion Cliffs Wilderness
- **Note**: Trip included a short excursion up Buckskin Gulch from the trailhead area, but the main route follows the Paria River canyon
- **Dates**: April 4–8, 2026 (based on GPX timestamps)

## Files

| File | Purpose |
|---|---|
| `paria-trip-map.html` | The map — serve via `node serve.js`, open at `localhost:8080` |
| `build.js` | Reads all `photos/trip/*/captions.json`, extracts EXIF GPS + datetime, generates `trip-data.js` |
| `trip-data.js` | Auto-generated by `build.js` — loaded as a `<script>` tag so the map works without fetch |
| `serve.js` | Tiny Node.js static server (no deps) — required because `file://` blocks MapLibre web workers |
| `onx-markups-05052026.gpx` | onX export of the actual GPS track (3,517 points) |
| `photos/trip/{person}/` | One subdirectory per photographer; each has `captions.json` + JPEG files |

### Workflow

```bash
# After adding/editing photos or captions:
node build.js

# To view the map:
node serve.js        # then open http://localhost:8080/
```

## Photo data structure

Each person gets a directory under `photos/trip/`. Their `captions.json` groups photos under shared captions:

```json
[
  {
    "caption": "Slot canyon - Full caption text here...",
    "photos": [
      { "file": "IMG_0351.jpeg" },
      { "file": "IMG_0414.jpeg" }
    ]
  }
]
```

`build.js` reads EXIF from every JPEG and enriches each photo entry with `lat`, `lng`, `routeFrac`, and `time` automatically. Optional per-photo overrides (`lat`, `lng`, `time`) and group-level overrides (`date`, `time`) are respected if present in the JSON.

**Current photographers:**

- **Jon** — 1 photo (first night's camp)
- **Lauren** — 6 photos across 4 caption groups (slot canyon, stars, petroglyphs, blooming cacti)
- **Maggie** — 1 photo

To add a new person: create `photos/trip/{name}/captions.json`, add their JPEGs, run `node build.js`.

## Tech stack

- **MapLibre GL JS** (v4.7.1) — open-source map renderer, supports 3D terrain natively
- **MapTiler** — provides the topo basemap style (`topo-v2`) and terrain-RGB elevation tiles
- **exiftool** — CLI tool used by `build.js` to batch-read EXIF GPS and datetime from JPEGs
- **GeoJSON** — route and photo markers are plain JS objects, no external data files

Why this combo: MapLibre is free and open, MapTiler's free tier covers a personal project, and the whole thing ships as one HTML file with no framework dependencies. `file://` is not supported due to MapLibre's web worker requirement — a local server is needed.

## Map features

- 3D terrain at 1.5× exaggeration (slot canyon walls read clearly)
- **Satellite imagery layer** (MapTiler `tiles/satellite` raster, opacity 1.0, default on) with toggle
- Topo basemap + extra hillshade layer for depth; satellite inserted above hillshade so route/labels render on top
- Desert sky/fog palette
- Route line with shadow, drawn from real GPS track
- Photo markers pinned to real EXIF GPS coordinates, numbered sequentially in chronological order (MDT) across all photographers
- Each photographer has a unique marker color: Gary `#e8a020` amber, Lauren `#2bb5a0` teal, Maggie `#b55ad0` purple, Jon `#4a9fd0` blue. Color shown on map markers, elevation chart squares, and right-panel person dot.
- Map markers are **circle icons only** — no popup thumbnails or captions on the map itself
- Clicking a pin triggers a faster 1.4s fly to that marker and loads it in the right panel
- Active marker highlights (white fill, colored border) so you always know your position in the story
- **Hamburger menu** (top-left of map, subtle frosted-glass style) — contains Overview, Toggle 3D, Satellite. Closes on item click or outside click. Satellite item gets orange tint when active.
- **Cinematic camera navigation** — Next/Prev buttons fly between photos with auto-computed bearing (faces direction of travel), 2.2s transition
- **Interstitial notes** — authored photo-less narrative beats (the `INTERSTITIALS` const in the HTML). Spliced into the photo sequence after a given 1-based photo number (`after: 2`); real photo ids are assigned before splicing so they never renumber. Camera parks at the lng/lat midpoint between the neighboring photos, zoomed out (`camZoom/camPitch/camBearing` in the const; defaults z10.5/p55/b-15). No map marker (null hole in the `markers` array keeps it index-aligned with `photos`); elevation-chart square is hollow dashed with y interpolated between neighbors; right panel swaps the photo for a styled note card (quote glyph + title + text + author). Notes have string ids (`n1`, …), always survive the people filter, and don't count in the overview photo total.
- **Deep links** — `?photo=N` (display number) or `?photo=n1` (note id) skips the intro and lands on that stop.
- **Per-photo viewpoint tuning** — when a photo is active, a "Viewpoint" row appears in the right panel. Set captures `{ lng, lat, zoom, pitch, bearing }` from the live map state; ✕ clear resets to auto. Persisted in `localStorage` under key `paria-viewpoints`. `stepTo()` uses the saved viewpoint if present, otherwise falls back to auto-compute (direction-of-travel bearing, z13.5, p65).
- **Debug panel** (`d` key) — live lng/lat, zoom, bearing, pitch + active photo EXIF bearing

## Right panel

Three-section flex column layout (`overflow: hidden` on the panel; only the body section scrolls):

- **`.rp-top`** (fixed) — Paria Canyon header + photo thumbnail
- **`.rp-body`** (scrollable, `flex: 1`) — title, person, date, caption, viewpoint tuning row
- **`.rp-footer`** (fixed, pinned at bottom) — Prev/Next nav buttons + progress counter (`X of Y`)

Displays per-photo:
- **Title** — auto-derived as text before ` - ` in the caption (e.g. "Slot canyon", "Stars")
- **Person** — title-cased from the directory name (e.g. "Lauren", "Gary")
- **Date · Time** — date from captions.json or EXIF; time auto-derived from EXIF `DateTimeOriginal`
- **Caption** — full text from captions.json; color `#999` (light gray, readable on dark bg)

### Photo thumbnail
- Container `aspect-ratio: 16/9`, background `#161616` (matches panel)
- `object-fit: contain` — full photo always visible, no cropping; portrait photos letterbox within the 16:9 box
- **Click to open lightbox** — fullscreen overlay (`rgba(0,0,0,0.9)`), fades in/out via CSS `opacity` transition (0.25s ease). Close via: ✕ button (top-right), click the dark background, or Esc key.

## Data

**Route**: Downsampled from 3,517 raw GPS points to 154 points (every 23rd point, keeping first and last). Stored inline in the HTML as a GeoJSON LineString. Also duplicated in `build.js` for `routeFrac` computation.

**Elevation profile**: `[route_fraction, elevation_meters, local_hour_MDT]` — 154 points extracted from GPX `<ele>` and `<time>` tags. Day transitions (overnight camps) are detectable where `hour` drops by >2 between adjacent points. Transition fracs: ~0.3308 (end Day 1) and ~0.6653 (end Day 2).

**Photo markers**: Real trip photos from `photos/trip/`, loaded dynamically via `window.TRIP_DATA` (generated by `build.js`). `loadPhotos()` in the HTML reads `TRIP_DATA`, flattens all persons' caption groups into individual photo entries, sorts them chronologically by MDT date+time, and reassigns sequential IDs after sorting. Each resolved entry:

```js
{ id, person, color, lng, lat, date, time, title, caption, img, bearing, routeFrac, sortKey }
```

`build.js` emits a per-photo `date` field (in addition to the group-level `date`) when EXIF reveals the photo was taken on a different day than the group — e.g. a photo grouped under a Day 1 caption but actually shot Day 2 morning. `loadPhotos()` uses `ph.date ?? groupDate` so sorting is always correct.

**EXIF fields used by `build.js`**:
- `GPSLatitude` / `GPSLongitude` — shot location → `lat`, `lng`, `routeFrac`
- `GPSDateTime` — UTC timestamp from GPS satellites → primary source for `date` and `time` (converted to MDT, UTC−6)
- `OffsetTimeOriginal` — phone's UTC offset (e.g. `"-07:00"`) → used to normalise `DateTimeOriginal` to MDT when GPS timestamp is absent
- `DateTimeOriginal` — local clock time → last-resort fallback only; assumed MDT if no offset available

**Timezone situation**: The trip crossed the Utah/Arizona border (Utah = MDT UTC−6, Arizona = MST UTC−7 year-round). Phones auto-switched at different times:
- Gary: MDT (`-06:00`) throughout ✓
- Maggie: MDT (`-06:00`) throughout ✓
- Lauren: switched from MDT → MST after Apr 4 ~2:13 PM (mid-trip); 4 photos had times 1h behind
- Jon: MST (`-07:00`) throughout; 1h behind MDT for his single photo

`build.js` resolves this by using `GPSDateTime` (always UTC, always correct) as the authoritative timestamp, falling back to `DateTimeOriginal + OffsetTimeOriginal` normalised to MDT, then raw `DateTimeOriginal` as a last resort. All displayed times are MDT.

**EXIF fields available but not yet wired**:
- `GPSImgDirection` (tag 17, ref T = true north) — exact camera bearing when shot (stored as `bearing` on each photo object, visible in debug panel `d`, not yet used for `flyTo`)
- `GPSAltitude`, `GPSSpeed`

**`routeFrac` computation** (in `build.js`): snaps each photo's GPS coordinate to the nearest of the 155 route waypoints using Haversine distance, then returns that waypoint's cumulative arc-length fraction of total route length.

**Trip timing** (local MDT, UTC-6):
- Day 1 (Apr 4): 11:21am – 7:24pm
- Day 2 (Apr 5): 9:16am – 5:35pm
- Day 3 (Apr 6): 9:28am – 4:05pm
- Total distance: 33.5 miles, elevation range 955m–1396m (3,133–4,580 ft)

## What was ruled out (and why)

| Option | Why skipped |
|---|---|
| Paper maps (Nat Geo #859) | Great reference, wrong shape for a digital artifact |
| Avenza/Apogee digital quads | Locked to their app, no customization |
| Raw USGS GeoTIFFs | Free and authoritative, but requires hand-tiling rasters |
| USGS 1m LIDAR DEMs | Incredible data, 5GB / 27 tiles — overkill for a trip page |
| Google Earth Engine | Optimized for analysis at scale, not a static trip artifact |
| CalTopo embed | Great cartography, not designed to bundle into custom JS |
| Matching onX 3D | Multi-month project; wrong battle — build what onX *can't* instead |
| `fetch()` for captions.json | Blocked by `file://` CORS policy — replaced with `build.js` → `trip-data.js` script tag |

## Elevation chart (canvas)

Drawn on a `<canvas>` inside `#elevation-strip`. Key implementation notes:
- Canvas pixel dims must be set to `W * devicePixelRatio` for crisp rendering on retina; CSS dims stay in logical px
- Time-of-day background: colored `fillRect` strips per profile segment using `createLinearGradient`; color stops in `timeToRGBA(h)` map hour → `[r,g,b,a]`. Current palette: blue morning → bright peak sun 12–4p → cool blue-purple evening
- Overnight camps drawn as near-black bands at the transition fracs, labeled "camp"
- Photo squares hit-tested on click with 14px radius; hover shows time + elevation tooltip
- `drawElevationChart(activeIdx)` called from `stepTo()`, `resetView()`, and `resize`

**Performance architecture:**
- Static layers (time gradients, camp markers, elevation fill/line, y-axis labels) rendered once into an offscreen `<canvas>` via `buildChartCache(W, H)`. Each `drawElevationChart` call blits the cache with a single `ctx.drawImage()` then draws photo squares on top. Cache invalidated on resize.
- `ELEV_MIN`, `ELEV_MAX`, `ELEV_RANGE` precomputed at parse time from the static profile. Photo pixel positions (`photoPos`) precomputed per cache build and reused by the draw loop and click handler.
- Mousemove handler is rAF-throttled: drops intermediate events, processes only the latest pointer position once per frame.

## Satellite layer

MapTiler raster source:
```js
{ type: 'raster', url: `https://api.maptiler.com/tiles/satellite/tiles.json?key=${KEY}` }
```
Layer added **before** `'hillshade'` in the `addLayer` call so topo labels and route render on top. Toggled via `setLayoutProperty('satellite-layer', 'visibility', ...)`. Default: on.

## Per-photo camera bearing (deferred)

EXIF `GPSImgDirection` is stored on every photo as `bearing` (true north degrees). Wired into the photos array but **not currently used** for `flyTo` — `stepTo()` uses either the saved `viewpoint` (if set) or `bearingBetween()` auto-compute (faces direction of travel). The EXIF bearing was tried as the `flyTo` bearing but often showed occluded terrain. Debug panel (`d`) shows active photo's EXIF bearing alongside current map bearing for comparison. The per-photo viewpoint system is the intended replacement.
